# ADR 0004：暂缓 SQLite 与实时事件采集

- 状态：被 [ADR 0013](0013-process-event-delivery.md) / [ADR 0014](0014-event-persistence.md) 取代（Phase 2.5–2.6 已引入事件采集与 SQLite 事件历史）
- 日期：2026-10-29

## 背景

最终产品需要本地事件、审计和恢复记录。但第一阶段没有持续传感器，也没有写操作；此时建立数据库会收集敏感数据，却没有形成完整的保留、访问控制和恢复模型。

风险：仅接入 ETW 事件或先建数据库，容易把“有日志”误当成“有覆盖”，也无法解释事件丢失、权限不足和传感器异常。

## 决策

- v0.1.0 不引入 SQLite，不持久化扫描结果。
- 扫描结果仅保存在前端内存。
- 不接入 ETW、文件系统实时监控或网络监控。
- 首页显示“状态未知”和“尚未实现”，不伪造实时数据。
- 后续必须先定义事件 schema、事件丢失语义、传感器健康状态和本地数据控制策略，再实现持久化。

## 后果

- 重启应用后没有扫描历史；无告警队列。
- 首页无法提供“最近检查”持久记录。
- 数据库迁移和恢复机制尚未编写。
- 产品变得更安全、更透明，但功能较少。

## 后续前置条件

1. 事件字段、规则 ID、来源和盲区契约固定。
2. 每类事件有真实数据源、测试和丢失/延迟行为。
3. SQLite 数据位置、访问控制、保留期限、删除/导出方法明确。
4. 首页状态从传感器健康而非静态文案计算。
5. 高影响动作有快照与恢复记录后才允许把它写入审计库。

## 后续设计（仍未实现）

2026-10-29 Phase 1.2 新增 [ADR 0008](0008-sensor-health-and-protection-state.md)（Sensor Health 与保护状态派生）和 [ADR 0009](0009-sqlite-audit-storage.md)（SQLite 审计存储与历史可用性）两份设计契约。两者均为设计接受、尚未实现；代码仍未引入 ETW 会话或 SQLite 写入，本 ADR 的暂缓决策继续有效。
