# ADR 0005：应用级 Tauri 命令 ACL

- 状态：接受
- 日期：2026-10-29（Phase 1.1）

## 背景

审计指出，原 capability 只列出 `core:default`，不能证明五个自定义命令有清晰的 ACL
语义。Tauri 2 的应用命令通常由 `generate_handler!` 注册，但这只是存在性白名单，
并不等于 capability 授权。

Tauri 2.12 提供 `tauri_build::AppManifest`，可为应用命令自动生成
`allow-<command>` / `deny-<command>` 权限。相关实现位于
`tauri-build` 的 ACL 构建支持与 `tauri` 的 runtime authority。

## 决策

- `src-tauri/build.rs` 通过 `AppManifest::new().commands(APP_COMMANDS)` 生成应用权限。
- 生成文件位于 `src-tauri/permissions/autogenerated/`，会提交并由 CI 检查其与当前命令清单同步；不要手工编辑这些 TOML。
- `command_names.rs` 是应用命令名的单一清单，供构建脚本与 capability 测试共用。
- `capabilities/default.json` 只授予五个 `allow-...` 权限，不授予不必要的
  `core:default`。UI 不使用任何 Tauri core 窗口/事件/文件插件命令。
- capability 仅作用于 `main` 窗口。
- 单元测试验证 capability 的 permission 集合与 `APP_COMMANDS` 完全一致，并禁止
  意外重新加入 `core:default`。
- `generate_handler!` 仍然是代码层的注册白名单；ACL 和 handler 清单必须同时维护。
- 已在 release 构建中启动应用并实际调用扫描/进程检查，确认 ACL 不阻断合法命令。

## 后果

- 自定义命令不再默认对所有未来 webview 开放；新增窗口必须显式加入 capability 并授权。
- 新增命令需要同步更新 `command_names.rs`、`generate_handler!` 和 capability；测试会
  捕获 capability/命令清单漂移，但 handler 注册仍需人工确认。
- 这并不提供参数级权限模型；参数边界仍由每个命令的强类型签名、PID/身份/长度校验
  和不接受任意路径/命令的设计保证。
- 移除 `core:default` 后，前端无法调用 Tauri 其他核心 API；这是有意的只读最小面。

## 未来约束

任何新的 IPC 命令或窗口都必须更新此 ADR/测试，且不得通过增加宽泛的 core 权限来
“修复”命令不可用。若未来引入远程 origin，需要单独的安全评审和 origin scope。
