# ADR 0009：SQLite 审计存储与历史可用性契约

- 状态：**部分实现**（Phase 2.6 采用 [ADR 0014](0014-event-persistence.md) 的事件历史 schema/路径；审计链、导出/删除界面和恢复快照仍未实现）
- 日期：2026-10-29（Phase 1.2）
- 范围：Phase 2 的本地审计/事件存储
- 实现说明：当前数据库为 `%LOCALAPPDATA%\app.sentinellite.desktop\SentinelLite\events.db`，schema v2，不加密；本 ADR 中未实现的部分不得视为已完成。

## 1. 路径、权限与归属

- 默认数据库：`%LOCALAPPDATA%\SentinelLite\data\events.sqlite3`。
- 目录和数据库只授予当前 Windows 用户访问；应用以普通用户运行，不使用管理员权限创建或修复数据库。
- 如果路径解析到 UNC、设备命名空间、重解析点或权限不可控位置，禁用持久化并显示“历史不可用”，不得静默降级为无历史。
- 数据库不是漫游数据，不随用户配置文件上传；不通过网络共享访问。
- 未来若引入高权限代理，数据库归属和 ACL 必须另立 ADR；UI 不得直接持有数据库路径写能力。
- 打开前检查目录/文件 ACL、符号链接/重解析点和归属；失败则只读禁用，不尝试“修复”安全设置。

## 2. Schema 版本与迁移

拟采用表：

- `schema_migrations(version INTEGER PRIMARY KEY, applied_at TEXT NOT NULL, checksum TEXT NOT NULL)`
- `events(event_id TEXT PRIMARY KEY, observed_at TEXT NOT NULL, received_at TEXT NOT NULL, sensor_id TEXT NOT NULL, event_type TEXT NOT NULL, risk_level TEXT NOT NULL, pid INTEGER, process_identity TEXT, process_started_at TEXT, file_path_hash TEXT, evidence_json TEXT NOT NULL, dropped_context INTEGER NOT NULL DEFAULT 0)`
- `sensor_health_samples(...)`（后续按 ADR 0008 定义）
- `operations(...)`（未来处置审计；本阶段不存在写入动作）

迁移规则：

1. 仅允许向前迁移；每个迁移在事务内执行并写入版本和校验和。
2. 迁移前创建受控备份（或明确标记不可备份），失败回滚并保留旧版本。
3. 禁止在迁移中执行无界表重写；大表分批，带进度与上限。
4. 版本未知/更高时拒绝写入，进入“历史不可用”状态；不自动删除数据库。
5. 迁移失败不得以空数据库冒充成功历史。

## 3. WAL、事务与完整性

- 默认评估 `journal_mode=WAL`：单写入者/多读取者场景可改善延迟，但会生成 `-wal`/`-shm` 文件，必须与主数据库同级同 ACL，且 checkpoint 有界。
- WAL 适用条件：单进程写入、明确 checkpoint 周期、启动/关闭清理、演示掉电和磁盘满行为；否则回退 `DELETE` 日志模式。
- 审计写入使用显式事务；动作成功/失败、部分成功和恢复信息必须在同一事务边界内保持一致。
- `synchronous` 默认采用对审计更保守的设置（`FULL`）；若更改为 `NORMAL`，必须记录耐用性与丢失窗口并测试。
- 每次打开执行 `PRAGMA integrity_check`；完整启动可执行 `quick_check`，周期任务可执行完整检查。
- 若 `integrity_check` 失败：
  - 立即停止写入和读取历史；
  - 保留原文件，不做自动删除/重建；
  - 显示“历史不可用：数据库完整性检查失败”；
  - 记录不会伪造“无威胁”/“无事件”；
  - 只在用户明确同意后尝试导出或另建数据库。
- 事务失败：有界重试；持续失败转入降级/不可用，保留错误与丢失计数；不得跳过事务继续假装已记录。

## 4. 保留上限

必须同时实施三种上限，以先到者为准：

1. **时间上限**：例如 30 天的原始事件（具体值需用户可配置并经测试）。
2. **条数上限**：例如 1,000,000 条事件；按策略清理最旧记录。
3. **字节上限**：例如 512 MiB 数据库/WAL 总占用；达到上限时先 checkpoint/压缩，再按明确策略清理。

- 清理有独立事务、批大小上限和日志计数。
- 不得因为达到上限静默丢弃新事件；必须记录 `events_dropped`/保留策略降级并让 UI 可见。
- 任何保留策略删除都要可解释，不把审计当垃圾清理；用户应能查看/导出/删除本地历史。
- 不使用自动“压缩优化”作为安全结论；VACUUM 只作为受控维护操作。

## 5. 字段与输入边界

- 所有 SQL 使用绑定参数；禁止拼接 SQL、表名、排序字段或 JSON。
- 事件、规则、路径、错误和 UI 字符串都有明确最大长度；超限截断并标记，不静默丢弃。
- 所有字符串入库/出库前去除或转义控制字符；UI 使用文本渲染，不使用 HTML。
- 不存储凭据、密码、键盘输入、屏幕内容或浏览器秘密；不默认存储完整命令行（若未来需要，必须单独隐私评审和长度/脱敏规则）。
- 文件名/路径可先规范化/哈希用于关联，原始路径必须受长度上限与隐私策略控制。
- JSON evidence 必须限制字节大小、数组长度和嵌套深度。

## 6. 有界队列与事件丢失

- 事件队列固定容量（建议 4096，最终以测量确认）；数据库写入队列独立且有界。
- 进入数据库队列前/后的事件状态必须可统计：received、queued、processed、dropped、delayed。
- 队列满：
  - 优先背压/等待，但等待必须有上限；
  - 超过上限则增加 `events_dropped`，产生可见 DataIssue/健康降级；
  - **不得静默丢弃**或覆盖未处理事件。
- 写入失败重试有界，不能无限保留内存事件。
- 数据保留清理与传感器事件写入不能互相无限阻塞；必须定义优先级和超时。
- 事件时间与写入时间分开存储；延迟处理时使用原始事件时间。

## 7. 历史不可用语义

以下情况必须显示“历史不可用/历史降级”，而不是“无威胁”：

- 数据库不存在但从未初始化；
- 数据库打开失败、权限不足、路径不安全；
- 迁移失败或版本不兼容；
- `integrity_check` 失败；
- 写入队列满或数据库只读；
- 保留策略截断历史；
- 持久化功能尚未实现。

UI 必须区分：

- “无匹配事件”与“没有风险”；
- “历史不可用”与“真正零事件”；
- “保留策略删除旧记录”与“从未发生事件”；
- “写入暂时失败”与“数据库完整”。

## 8. 测试规范（实施前）

1. 数据库不存在、权限不足、目录重解析/UNC、只读目录的禁用与 UI 语义。
2. 多版本迁移成功、回滚、校验和不匹配、版本过新。
3. WAL/非 WAL 的打开、checkpoint、WAL 上限和文件 ACL。
4. 时间/条数/字节三种保留上限及先到者优先；删除失败/磁盘满。
5. `integrity_check` 失败时停止读写、保留文件、UI 显示历史不可用。
6. 事务失败、重试上限、部分成功与恢复记录。
7. 绑定参数、超长字符串、控制字符、超大 evidence JSON。
8. 事件队列/写队列满时 dropped 计数与降级，绝无静默丢失。
9. 历史不可用时 UI 不显示“无威胁”或“从未发生事件”。
10. 未来处置动作的审计与恢复记录必须与动作本身同一事务边界，且不可伪装成功。

本 ADR 不实现 SQLite；Phase 2 只有在该契约的存储、路径权限、损坏恢复和 UI 语义测试全部通过后才能启用本地历史。
