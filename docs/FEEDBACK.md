# 误报、漏报与反馈

仓库公开后，普通误报与功能问题通过 GitHub Issues 反馈；安全漏洞必须走 [SECURITY.md](../SECURITY.md) 的私密报告渠道，不要发公开 Issue。

## 误报反馈

“误报”指产品把正常软件、正常启动项或合理配置描述成不值得信任的风险。请尽量提供：

- SentinelLite 版本、Windows 版本与架构。
- 触发条目对应的规则 ID（例如 `INV-001`、`INV-COMPONENT-000`、`STARTUP-003`、`STARTUP-005`、`AFF-001`、`PROC-001`）。
- 若是完整性/分类问题，请说明 `truncated` 状态、软件分类标签和路径状态（Present/Missing/AccessDenied/Unknown）。
- 风险标签与置信度。
- 你期望的判断，以及为什么认为当前判断不准确。
- 可公开的最小复现方式或虚构化示例。

请不要提交：

- 真实文件、可执行样本、注册表全量导出、完整命令行或账号凭据。
- 他人的个人信息、浏览器数据或未脱敏截图。
- 正在利用中的漏洞细节（请走私密渠道）。

## 漏报与覆盖缺口

如果某类行为没有被发现，请先确认它是否属于 [检测覆盖](DETECTION_COVERAGE.md) 声明的范围。当前没有实时监控，许多行为预期不会被发现。对于已声明覆盖的路径，提交时请说明：

- 数据来源（软件盘点、启动项、进程快照等）。
- 预期出现的条目/证据与实际结果。
- 当时是否权限不足、进程已退出、路径 AccessDenied、查看器截断或目标不可访问。

未知、证据不足、AccessDenied、截断和未覆盖不是同一种情况；反馈中请避免把它们都称为“漏报”。

## 记录渠道

第一阶段不保存扫描历史，因此请自己保留检查时间、规则 ID 和必要的脱敏截图。项目目前没有遥测上传，也不会自动把反馈发送到任何服务器。

## 处理原则

- 误报修复优先级不低于新增检测规则。
- 需要先补正常案例与回归测试，才能提高规则的自动处置能力（当前没有自动处置）。
- 不会因为某品牌或某个软件被反馈就加入无证据黑名单，也不会为了减少误报而把 Unknown 强行改成 UserSoftware。
- 不承诺固定响应时限或漏洞赏金。

## 安全边界

误报/漏报反馈不能替代独立安全审计；产品当前也未经完整审计。修复结果需通过测试和证据复核，且仍不得声称能识别所有恶意软件。
