# 已知限制

这些限制是产品当前真实状态的一部分，不应在发布说明或宣传中省略。

> **Source-only release:** 本次 0.1.0 公开仓库只提供源码，不提供 Windows 安装包、`sentinel-lite.exe`、`SentinelLiteSensor.exe` 或原生 `.node`。文中涉及安装包和二进制的内容描述的是源码构建后的本地产物或历史构建记录，不是本次 Release 的下载资产。

## 覆盖与状态

- 主应用首页已接入独立传感器的只读状态、健康、事件计数与运行时间；“进程事件”页已接入实时事件、SQLite 历史和基础行为分析；Phase 3 切片 1 增加用户主动触发的 Defender/防火墙只读快照，切片 2 增加服务与计划任务只读盘点；没有告警队列、通知或处置；整体保护状态仍为“状态未知”。独立 `SentinelLiteSensor.exe` 能在管理员下采集进程 start/stop、标准化事件、配对、投递事件、统计丢失并检查残留。
- 0.1.0 不提供应用内启动/停止传感器，也不提供 UAC/`runas`/`ShellExecuteW` 提权入口；独立 `SentinelLiteSensor.exe` 必须由管理员从源码构建并在应用外手动运行 `--serve`。本次源码发布和本地构建的安装包都不包含该二进制；本次源码发布本身不提供安装包或传感器二进制。传感器未运行时首页只显示静态“当前版本暂不支持在应用内启用实时保护”，不会发起启动请求。应用不静默提权、不自动启动、无处置。
- Phase 2.4–2.5 的标准化事件通过有界投递窗口交付给主应用；事件投递窗口默认 4,096 条、可配置 64–65,536，无人读取时会淘汰最旧记录并让客户端看到游标过期。投递淘汰不是 ETW 丢失，也不会使采集健康失败；应用未运行时事件最终会丢失。传感器等待任一客户端确认 `SessionEnd` 最多 2 秒，随后再保留端点 2 秒供第二个消费者读取；这仍是有界尽力而为，任意慢/多客户端可能错过尾部。
- Phase 2.6 的 SQLite 历史只在主应用运行且能连接传感器时写入；应用关闭期间的事件不会进入历史。数据库不加密、没有防篡改/完整性签名；本地管理员仍可修改。查询和写入共享连接互斥锁，极端长查询会短暂延迟摄取（但不会延迟 ETW）。新的 `SessionEnd` 现在携带 `final_stats`（ETW 丢失/实时缓冲丢失、管道计数、最终积压和关闭超时）；旧数据库中的历史会话没有该块，检测对这些旧记录仍显示未知。停止失败或存在残余 session 时 ETW 统计保持未知，不会填 0。
- Phase 2.7 实时列表只保留最近 500 条；完整历史依赖 SQLite。传感器断开后保留最后事件并明确标记中断，不能被当作当前完整活动。真实 UI 验证使用窗口截图/坐标点击，未建立 WebView2 自动化 E2E；未在多 DPI/多显示器/键盘全流程下复验。
- Phase 2.8 的规则只使用进程 start/stop、时间、PID/父 PID、映像和配对状态；没有命令行、文件、网络或内存证据。阈值是保守默认值，未用大规模正常/恶意样本校准，误报/漏报率未知；不能把 `suspicious`/`anomaly` 当作恶意判定。旧历史会话或最终统计未知时整体通常为 `indeterminate`/`data_insufficient`；新会话若保存了已知为零的最终统计，仍可能因样本/规则不足而为其他状态。
- 事件队列默认 4,096 条，可用 `--queue-capacity` 配置 64–65,536；满时丢弃最新事件并计入 `dropped_queue_full`，不阻塞 ETW 回调。`backlog` 包含消费者当前持有的事件，瞬时峰值可能为容量 + 1；实际 channel 占用严格不超过容量。真实机器 smoke 的峰值积压为 10–11，不能据此推断所有机器/高峰负载都足够。
- 配对状态有界：打开 Start 65,536、已关闭身份 65,536、待回补孤儿 Stop 4,096。达到上限会淘汰并计数（`closed_identity_evictions`、`orphan_stop_overflow`、`start_overflow`），并使健康失败关闭；极长时间/高流失会话可能因此降级。没有持久化，重启后不恢复旧会话的配对状态。
- 乱序 Stop 先以 `unpaired { stop_without_observed_start }` 发出；后续匹配 Start 时产生 `PairingRevision` 修正。没有持久化时，下游必须同时消费 revision 才能得到最终配对结果；SessionEnd 的配对摘要也反映最终状态。
- 传感器硬杀（`TerminateProcess`）无法写 summary、无法发送 SessionEnd，内存中的队列和未完成生命周期会丢失；硬杀仍可能留下 ETW session，需要管理员 `logman stop`。正常时长结束和 Ctrl-C 已验证会排空队列并写 summary。
- ETW `events_lost`/`realtime_buffers_lost` 与管道 `dropped_queue_full`/`dropped_consumer_gone` 分开统计；IPC 的 `events_dropped` 是解码错误 + 管道丢弃的聚合值，UI 的“处理丢弃”因此包含队列丢弃，不能与 ETW 丢失混为一谈。
- 缺失事件时间戳、部分/截断 ImageName 会计入 `partial_events` 并使健康降级；缺失父 PID/ImageName 在标准化事件中显式记录，不编造。
- 真实机器验证：20 秒管道 smoke（20 events、20 processed、9 paired、0 dropped、peak backlog 11、session end completed、exit 0、无残留）；Ctrl-C `--serve` smoke（28 events、28 processed、backlog 0、session end interrupted、2 个未完成 Start、无残留）；提权 probe（active/granted、17/17、`health_ok=true`、`last_error=null`、随后 Ctrl-C、无残留）。队列满载/消费者退出/关闭超时/sink 错误仅为自动化测试，不是实机注入。
- 独立传感器只覆盖进程 start/stop；Stop 的 ANSI ImageName 仅作诊断，smoke 的 3/3 长名证据只验证 Start ImageName。
- 传感器无法在 `TerminateProcess` 硬杀后于进程内清理 ETW session；Ctrl-C/Ctrl-Break 走停止/清理路径，控制台关闭/关机只保证尝试 stop，不保证 JSON 报告保存。硬杀可能留下 session，需管理员用 `logman stop` 或后续稳定 session 所有权设计处理。
- 传感器停止失败、长时间运行、丢事件注入和并发多会话仍未实机覆盖；真实 STOP 失败注入未执行。
- 传感器 IPC 提供只读状态和只读事件批次，不支持停止/配置/任意命令；首页状态每 4 秒查询一次，事件页每 1 秒推进游标。事件批次上限 128 条/256 KiB；游标过期/超前显式返回。运行时事件服务器线程故障由客户端查询失败观察，状态管道不直接探测该线程。
- 状态管道使用固定端点、当前用户/SYSTEM/BA DACL 和 Medium mandatory label；同用户进程可抢占管道造成传感器 IPC 不可用（传感器会降级，不会误报健康），同用户进程也可查询非敏感状态；管理员级伪造超出当前威胁模型。Phase 2.3 的最终二进制实机验证使用非提权 `sentinel-lite.exe`（`06628fd...`）连接提权 `SentinelLiteSensor.exe`（`ae4314fe...`），在 Active+Healthy 与 Active+Unhealthy 状态均完成查询；旧 `4505268a...` Medium probe PASS 仍为历史证据。跨用户 DACL 拒绝、并发压力和长时间运行仍未验证。
- 传感器被硬杀后状态管道会消失，但 ETW session 可能残留；Phase 2.3 的停止过渡测试使用 force-kill 后由管理员 `logman stop` 清理，最终无残留；这不改变“硬杀可能留下 session”的限制。主程序看到的 `stopped`/`unavailable` 只说明 IPC 链路状态，不能证明没有 ETW 残留，仍需管理员用 `logman query -ets` 检查。
- 原生防护状态只在用户点击后读取一次快照；不持续监控，不读取 Defender 策略、排除项、ASR、篡改保护或防火墙规则，不验证实际拦截能力；第三方 AV 的 SecurityCenter2 状态未读取。查询失败、字段缺失或无权限时保持未知，但这仍不能证明系统未受保护或未受攻击。WMI 的 ConnectServer/ExecQuery 没有独立超时（仅枚举 Next 为 5 秒）；极端 WMI 卡死时查询可能长时间不返回，但不阻塞 WebView，也尚未实现取消。
- 服务与计划任务只在用户点击后读取一次快照，结果仅在内存、不写入 SQLite；不持续监控；静态路径关联已实现，但没有实时/跨重启关联或持久化关联历史。服务最多 1,024 条（8 秒）、任务最多 1,024 个/256 文件夹/16 动作（10 秒）；超限或集合计数失败显示不完整，不再统一解释为“达到安全上限”。服务路径只保留可执行文件、丢弃参数；任务不读 Arguments、WorkingDirectory、触发器、计划/条件或上次运行结果；不验证目标文件存在性、签名或哈希。返回 WebView 前会脱敏个人账户和用户目录段；内部关联仍使用原始路径。
- 普通用户可能无法读取个别服务/任务/文件夹（本次实测 1/763 服务访问拒绝）；条目显示 `accessDenied`/`partial`，不会当作正常。Task Scheduler COM 与 SCM 调用本身不可中断；时间上限只在枚举循环间检查，极端卡死可能让后台命令长时间不返回，但不阻塞 WebView。
- 服务/计划任务枚举包含驱动和隐藏任务；这是盘点范围，不代表它们已启用、会运行或具有安全意义。
- 软件盘点仅覆盖传统 Uninstall 注册表项，不含 Store/AppX、MSIX、便携软件；不同视图/用户范围的同名登记记录不自动合并，UI 显示“卸载注册项”而不是唯一软件数。无 DisplayName 的注册项跳过并计数。
- HKCU 只读共享视图一次；修复前 187 条历史结果含 WOW64 重复，HKCU 修复后本机只读验证为 183 条唯一注册表条目（具体随机器变化）。
- 启动项仅覆盖 Run/RunOnce 与启动文件夹；不含计划任务、服务、Winlogon、IFEO、组策略、WMI 永久订阅、AppInit_DLLs、浏览器扩展等。`.url`、MSI 通告式快捷方式和无法由 ShellLink 解析的目标保留为部分未知。
- 软件资产关联只使用当前快照的静态路径：精确路径、安装目录包含和同名文件弱线索；不读取命令行/参数，不验证文件存在性、签名、哈希或行为，不做实时或跨重启归属，也不建立完整资产图。宽泛根、8.3 短名、junction、符号链接、环境变量、UNC/设备路径和带参数文本不参与或标记不可比较；同一目标多个软件候选全部保留并标记歧义。来源部分读取/不可用/截断时显示证据不足，不能据此断言没有关联。关联结果只在内存，不写 SQLite。软件卸载入口只记录存在性，不返回完整命令，不执行卸载器。
- 安全态势概览只组合已有原生防护与资产关联快照，不是整体安全结论：`complete` 只表示来源可读且未截断，不表示系统没有恶意软件；不提供 0–100 分数或“保护正常”状态。概览不自动刷新，系统状态变化后快照可能过期；刷新失败会清空旧结果。真实 release 本次显示 68 条关系（49 进程、11 服务、8 计划任务/启动项）、13 个软件有线索、171 个证据不足、0 个未匹配；3 个来源已读取、2 个部分读取、0 个不可用。关系数量会随当前进程变化，不应与另一次探针的 62 条直接比较。
- 概览中的计划任务/启动项、进程/服务和弱线索区块可能重复展示同一条关系（弱线索是交叉筛选）；这是展示分组，不是重复采集。软件状态只展示前 8 个有路径线索的软件，完整清单在软件盘点标签。
- 原生防护在真实机全部开关为已启用；不能据此推断拦截能力、规则完整性、企业策略或第三方 AV 状态。`amServiceEnabled=false` 摘要 P2 已修复，但其他未验证的字段语义仍以 `KNOWN_LIMITATIONS` 为准。
- 软件分类仅依赖 Uninstall 注册表字段；ParentKeyName/ReleaseType 可能不足，Driver/Runtime/Security 分类常保持 Unknown，不猜测。
- 系统组件/NoRemove/组件类条目不应用普通软件缺失卸载信息规则；这减少误报，但仍可能受注册表字段缺失影响。
- SystemComponent/NoRemove/ParentKeyName/ReleaseType 的类型不符、无效值或读取失败会保留为显式状态并阻止回退为普通用户软件，分类通常保持 Unknown；这类条目仍需人工核实，不能仅凭字段异常判定恶意。
- 未检查浏览器扩展、主页、搜索引擎、代理配置。
- 未集成 YARA-X、Sigma 或自定义文件内容扫描。
- Defender WMI 查询只在 `MSFT_MpComputerStatus` 返回实例时有效；第三方 AV 接管、提供程序损坏或策略禁用会使结果保持未知。防火墙 `INetFwPolicy2` 只读取三个配置文件的启用位，不读取规则或有效拦截状态。
- 服务配置使用 SCM `QueryServiceConfigW`；测试机 Windows 11 26200 上 64 KiB 缓冲区会返回 `RPC_X_BAD_STUB_DATA (1783)`，因此使用 8 KiB 起始、32 KiB 上限；超过上限的服务配置保持部分未知。任务计划程序集合使用 1-based 索引；本机实测 192/192 任务可读，但其他系统/权限模型可能不同。

## Windows API 限制

- 处理器亲和性只反映当前处理器组；超过 64 个逻辑处理器或跨组场景不完整。
- 无法从现有接口判断谁在何时修改亲和性；UI 只显示“不可观察”。
- CPU 使用率是约 500 ms 的短时采样，不是任务管理器等价数据，也不能单独说明资源滥用。
- 部分受保护进程路径不可读取；读取权限不足显示为访问被拒绝。
- 进程检查使用创建时间身份令牌，但受保护进程可能无法读取身份/路径；此时不能进行亲和性检查。
- 磁盘文件可能在进程启动后或签名/哈希读取之间变化；哈希/签名不验证内存映像。
- 签名只验证磁盘文件，不验证运行内存；不联网、不检查吊销；系统目录签名通过 verifysign 回退读取。
- 文件签名状态、发布者名称和软件名称均可能被欺骗，不能单独作为安全结论。
- 启动文件夹中的 `.lnk` 只读取目标路径和“参数/工作目录是否存在”的布尔值；不读取参数/工作目录文本、不调用 ShellLink Resolve、不执行目标。`.url` 未解析。
- 普通用户可能无法读取个别 Run/RunOnce 键、启动文件夹或快捷方式；来源级和条目级显示 `accessDenied`/`error`/`partial`，不会当作空值或正常。
- 启动项来源“确认不存在”（`exists=false`）与“无法确认存在性”（`exists=null`）分开；缺失可选键/文件夹不使整体结果变成 partial，但不能解释为已读取成功。
- 启动文件夹中的 desktop.ini/Thumbs.db 等 Windows 文件夹元数据文件会被跳过，不计为启动项；跳过的数量以 `startupFolderMetadataSkipped` 报告。
- Windows 启动审批状态未核验，不能确认启动项实际启用。
- 路径状态现在区分 Present/Missing/AccessDenied/Unknown；AccessDenied 不再合并为 Missing。
- 未加引号的路径歧义采用保守启发式，只确保不误判为缺失并显示候选路径；不能覆盖所有 Windows CreateProcess 解析情况。
- 注册表每视图最多 512/256 项、软件总 1024、软件每个 Uninstall 视图 512、软件字符串 2048、DisplayIcon 结果路径 1024、8 秒、启动项总 512、启动项每个注册表视图/文件夹 256、值名称 512、值文本 2048、目标路径 1024；进程快照最多 2048 项，进程名称 512、路径 4096 字符；达到/超过上限会使结果 truncated，不能视为完整。
- 软件/启动项/进程 UI 分页 50 行；问题列表本身未分页。

## 产品与安全

- 当前版本没有任何清洗、卸载、删除、终止进程、修改启动项或修改亲和性的操作。
- `ProtectionState::Protected` 已从代码删除，直到有真实传感器健康模型；首页单独显示传感器运行/健康状态，但整体保护状态仍为“状态未知”。
- 亲和性正常只产生“亲和性范围内未发现异常”的局部结论；整体进程始终为证据不足（没有行为证据）。
- 有本地 SQLite 进程事件历史，但没有数据库加密、审计链、导出/删除界面、恢复快照、告警持久化或自动清理确认 UI。
- 没有安装包签名、自动更新、崩溃报告或遥测。
- 没有经过完整安全审计、渗透测试、恶意样本测试或正式性能基准测试。
- 一次干净 release、默认首页空闲 10 秒采样的整个进程树内存为 365.0 MB 工作集 / 195.3 MB 私有内存，**未达到 <100 MB 的初始目标**；主进程为 25.6 MB，但 WebView2 子进程也必须计入。CPU 在该窗口内低于计时分辨率。尚无持续监控负载或长时间数据。
- 未对真实 PUP/恶意软件建立误报/漏报率；不得宣传检测覆盖率。Phase 2.8 的 4 条规则只覆盖进程频率、配对覆盖和生命周期一致性，且证据来自正常管理活动测试，不是恶意样本。
- 不具备管理员权限下的对抗能力，不针对 Rootkit、内核攻击或已控制主机的攻击者。
- 当前 Windows 11 x64 环境验证过；Windows 10、ARM64 等未验证。
